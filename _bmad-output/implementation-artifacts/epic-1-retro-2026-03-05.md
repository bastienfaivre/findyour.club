## Successes

1. **100% story completion with strong test coverage** — 187 tests at epic close, zero regressions across stories.
2. **Consistent knowledge transfer** — each story file's "Previous Story Learnings" section accumulated 11 patterns by Story 1.9, preventing the same mistakes from recurring.
3. **Good architectural self-correction** — two mid-story pivots (URL routing, admin login) reduced complexity when simpler approaches were identified during review. Both were the right calls.
4. **Clean security patterns established** — AES-256-GCM, Argon2, SHA-256 token hashing, totp_verified cookie, typed Server Action results, no client-side secrets — all consistently applied from Story 1.3 onward.
5. **ADR-001 ClubMembership** — the junction table decision (vs User.clubId) proved foundational; Stories 1.7–1.9 built on it cleanly.

---

## Challenges

1. **Mid-story pivots were costly** — URL routing pivoted in Story 1.4 (subdomain → path-based), admin login reworked in Story 1.5 (dedicated page → shared login). Both required story rework. Identified as discovery-during-review rather than planning failures.
2. **Server-side guards consistently incomplete on first submission** — missing self-transfer block (1.8), non-ACTIVE target validation (1.9), LAST_OWNER race condition (1.9). Caught in review but should be designed upfront.
3. **Quality gates not systematically enforced** — `pnpm tsc --noEmit`, `pnpm lint`, `pnpm audit`, `pnpm build` were run in some stories (e.g. 1.1) but not consistently documented across all stories.
4. **Multi-step flows not always designed for all paths** — race conditions and abandonment scenarios were discovered in review rather than designed upfront.

---

## Key Insights

1. **"Is this the simplest approach?"** should be asked before implementation, not during code review. The URL routing and admin login pivots were good outcomes, but the cost of reworking mid-story is real.
2. **Quality gates must be a hard pre-submission requirement** — `pnpm tsc --noEmit && pnpm lint && pnpm audit && pnpm build` before any story is marked done, and confirmed by reviewer before starting code review.
3. **Every multi-step flow needs a resilience review** — map all paths: user abandonment at each step, token/session expiry, concurrent requests, partial DB failures, input edge cases. Do this before writing implementation code.
4. **Guard completeness checklist** — auth, role, cross-entity ownership, self-action, status validation, try/catch on DB writes — must be verified on every Server Action before submission.

### Significant Discoveries Requiring Epic 2 Updates

The following gaps and architectural decisions were identified during this retrospective. Epic 2 stories **cannot start** until these are resolved.

**1. Enum casing normalization (schema migration)**
`ApplicationStatus` (pending/approved/rejected) and `ClubStatus` (active/suspended) use lowercase — inconsistent with `MembershipStatus` (PENDING/ACTIVE). Must be normalized to UPPERCASE before Epic 2.

**2. Application.country field missing**
The `Application` model has no `country` field, but `Club` requires one. The `/apply` form must include country selection. Requires schema migration.

**3. Dynamic ActivityType model (new architecture)**
`Application.activityType` is currently a plain `String`. The correct architecture is operator-managed dynamic types:
- New `ActivityType` model `{ id, name, slug (unique), createdAt, createdBy }`
- Application form: select from existing types + "Other" + free-text fallback
- Operator review: can create a new ActivityType before confirming approval
- Club model: gets `activityTypeId` FK
- Stories 2.1, 2.2, 2.3 ACs all need updating to reflect this

**4. Location architecture (new architecture)**
Club location is country-specific and on-demand (no pre-loaded data). Design:
- `SwissLocation { id, plz, name, canton; @@unique([plz, name]) }` — created on first use via upsert
- `Location { id, country, swissLocationId? }` — bridge model, extensible for future countries
- `Club.locationId` → `Location` → `SwissLocation` (for CH)
- `Application.locationId` → `Location` → `SwissLocation`
- Frontend autocomplete: `/api/locations?country=ch&q=` server-side proxy (calls OpenData Swiss API, caches results)
- Backend: upsert `SwissLocation` on approval, create `Location` bridge, link to `Club`
- Extensible: adding France = add `FrenchLocation` model + `frenchLocationId?` on `Location`
- For Epic 3 filtering: Switzerland uses canton + city filters; filter UI is country-aware

**5. `lib/slug.ts` missing**
Story 2.3 references a reserved slug list (21 entries) via `lib/slug.ts`. This file must be created and the reserved slugs defined explicitly.
